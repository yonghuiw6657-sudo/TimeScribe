### P0 发现并修掉的真问题（都是"不测就发现不了"的）

| # | 问题 | 后果 | 修法 |
| --- | --- | --- | --- |
| 1 | `.bat` 里写中文注释 | cmd 按 ANSI 解码，`@echo off` 失效、脚本逐行回显甚至报"文件名语法不正确" | **批处理文件只用 ASCII**；`tests/fix-bom.mjs` 会强制检查并拒绝非 ASCII |
| 2 | `.bat` 带 UTF-8 BOM | cmd 把 BOM 当命令的一部分，`@echo off` 变成 `?@echo off` | **`.bat` 绝不加 BOM**；`.ps1` 必须加 BOM（否则 PowerShell 5.1 下中文乱码）。`fix-bom.mjs` 自动纠正 |
| 3 | `for /f ... in (`` `"..." -File "..."` ``)` 内联引号 | cmd 解析失败，脚本从未被执行，退出码却是 0 | 改用 `call` 包一层；并把逻辑收敛到 PowerShell，`.bat` 只做转发 |
| 4 | 中文路径传给 `powershell -File` | 路径被 ANSI 解码弄坏，报"文件名、目录名或卷标语法不正确" | **入口脚本改成 ASCII 文件名** `launch.ps1`（双击用的 `启动.bat` 保持 ASCII 转发） |
| 5 | `Test-PortBusy` 只测 TCP 端口 | Windows 的 **HTTP.sys 会在 HttpListener 进程退出后继续替该端口接受连接**，于是每次双击都被误判为"已在运行"，真正的服务永远起不来 | 新增 `Test-ServerAnswering`：必须取到真实 HTTP 响应且内容匹配才算"已在运行"；端口被别的程序占用时明确报错 |
| 6 | `Start-Process -RedirectStandardOutput` 会阻塞父进程 | 输出管道被子进程持有，`启动.bat` 卡到超时（退出码 null） | `start-server.ps1` 只负责拉起并打印 PID，不等就绪；由调用方轮询端口 |
| 7 | 旧版 `serve.ps1 -Quiet` 静默失败 | 端口被占时"双击了但什么都没发生"，无从排查 | 失败写入 `server.log`；`server.pid` 记录真实进程号 |
| 8 | 测试自己留下的服务进程 | 端口残留 + HTTP.sys 预留，污染后续测试 | 测试结束显式 `taskkill` 服务进程并轮询确认端口释放（写成一条测试） |
| 9 | 静态检查规则过粗 | 把测试文件里的字符串（`http://0.0.0.0`）当成"外部引用"，误报 | 拆成两条：交付文件**完全不许有网络引用**；全目录**按主机名分类**，只禁止外部主机（本机地址除外） |
| 10 | 浏览器测试页没加载 app | DOM 断言全落空（测试页自己查不到 `#app`） | 改为同源 iframe 加载真实 app 再断言 |

### 已知环境限制（记录在案）

- `HttpListener` 场景下 `netstat -ano` / `Get-NetTCPConnection` 可能把监听者显示为 **PID 4（System/HTTP.sys）**，而不是真实的服务进程。因此：
  - 测试改为用 `server.pid` + `Get-Process` 校验"进程真实存在"；
  - 清理端口时同时按 `server.pid` 杀进程。

**关键结论（写进实现的约束）**

- **坏数据不白屏**：JSON 解析失败时，把原文另存到 `timetracker.corrupt.<时间戳>`，然后返回一份干净的空数据，界面照常启动。
- **旧数据自动补默认值**：缺 `settings` / `ui` 也能读，不需要写迁移脚本。
- **孤儿记录一律丢弃**：`projectId` 指向不存在项目的记录会被剔除并计数；父项目不存在的子项目会被**提升为顶层**而不是消失；出现第三层会被**压平成顶层**。
- **超长输入在这里兜底**：项目名截断到 30 字、备注截断到 100 字，界面不会因为脏数据被撑破。
- **配额不足抛可识别的 `QuotaError`**，与其他错误区分开，界面据此提示"请先导出备份"。
- **导入校验必须够严**：非本 app 文件、更新版本、缺列表、内容全部无法识别——一律拒绝且**不改动任何现有数据**（避免"导入一份空文件把用户数据清空"）。
- **测试清单与加载清单必须一致**：加了一条测试，比对 `manifest.json` 的全局模块、`index.html` 的 script 标签、`tests/selftest.html` 的 script 标签三者一致，防止测试环境和真实环境脱节。

**产物**：`js/storage.js`、`js/store.js`、`tests/manifest.json`。

## P2 · 时间与计算工具

**结果：全部通过**

| 测试文件 | 数量 | 结果 |
| --- | --- | --- |
| `tests/p2-format.test.js`（时长格式、时钟、日期、周边界、专注度） | 14 | 通过 |
| `tests/p2-summary.test.js`（统计汇总、扇形图分组与百分比） | 13 | 通过 |

**产出**：`js/calc.js`（全 app 唯一的统计口径来源）。

**关键结论**

- **日期一律用本地时区**：`toDateStr` 自己拼 `YYYY-MM-DD`，绝不使用 `toISOString()`（UTC 会差一天）。测试专门验证了本地 00:30 这种边界。
- **一周从周一开始**：测试覆盖周一当天、周日当天、跨月、跨年（2025-01-01 属于 2024-12-30 开始那一周）。
- **先四舍五入到分钟、再拆分小时**：3599 秒必须显示成 `1 小时`，不能是 `59 分`。
- **扇形图百分比用最大余数法**：保证各块相加**正好 100%**，不会出现 99% 或 101%。
- **专注度只认计时产生的记录**：手动补录没有暂停数据，算进去会把专注度虚高，因此 `source === 'manual'` 的记录不参与专注度，但仍计入累计投入。
- **孤儿记录一律忽略**：统计不会因为一条脏数据而变形。
- 测试里所有日期都**相对"今天"动态生成**，因此在任何一天运行都成立；另有一条测试遍历周一到周日，验证"今天/本周"的口径每天都正确。

**测试自身也出过两次错**（记录在案，说明为什么必须逐条核对而不是"看一眼差不多"）：
1. 我把"本周"期望写少了一条——手动补录记录同样落在本周内。
2. 我把"专注度"期望写成了不含手动补录的 1800，实际该项目另有一条上周的计时记录 900 秒也应计入。

两次都是**修正测试期望**（实现是对的），并补了注释说明口径，避免以后又改错。

**测试运行机制的重要修正（记在案，避免重蹈覆辙）**

- `--dump-dom` 在页面脚本还没跑完时就会取走 DOM（结果只剩 `RUNNING`）。
- 加 `--virtual-time-budget` 能等到结果，但**虚拟时间下 `setTimeout` 几乎瞬时触发、而 `Date.now()` 仍走真实时间**，两者脱节会让"计时时长"类断言失去意义（P4 一开始就是这么错了一次）。
- 最终方案：**测试页把结果 POST 到本机服务的 `/__result`，运行器轮询取回**。不做虚拟时间，计时测试跑在真实时间上。
- 另外发现：残留的服务器进程会在 HTTP.sys 里留下端口预留（`netstat` 显示 PID 4），导致新服务"看起来在跑、实际是旧的"。已用 `netstat` 清理并强制测试结束时回收。

## 第二轮修正：切后台不该暂停、关闭即结算

**来自实际使用反馈**：用了之后发现"切出浏览器再回来，计时变成了暂停"。

### 根因（我的设计错误）

`main.js` 的生命周期处理里，把**"切走浏览器"**（`visibilitychange` → hidden，切标签、切到别的应用、最小化都会触发）
和**"关闭页面"**（`pagehide`）接到了同一个处理函数上，而那个函数会把计时改成"暂停中"。
结果就是：只要切走一次，计时就被暂停了。

### 改成什么

| 时机 | 行为 |
| --- | --- |
| 切走浏览器 / 切到别的应用 / 最小化 | **不算中断**：计时按时间戳继续走；顺手把进度写进存储（心跳），便于被强杀时兜底 |
| 关闭页面 / 关闭浏览器 / 关掉应用 | **这一段直接结束**：结算到关闭那一刻，够阈值就保存成记录，不够就丢弃；不留"暂停中"的段 |
| 浏览器被强杀（没走正常关闭） | 下次打开时按**最后一次落盘时刻**结算并保存（绝不补算到"现在"），并明确告知用户 |

配套改动：

- 新增**心跳**：计时中每 15 秒把一次进度快照静默写进存储（`TTStore.patch`，不触发重绘）。
  这样即使被强杀，损失最多一个心跳间隔，而不是整段。
- 关闭时**不提供"撤销"**（页面马上就没了，撤销没有意义）；手动点"停止"仍然有撤销。
- `handlePageHide` 改名为 `finalizeOnClose`，语义从"改成暂停"变为"结束并保存"。

### 顺带堵住的一个隐患：同一段被记两次

改动"关闭即结算"之后，出现了一个新的现实风险：
**计时中如果你又双击了一次 `启动.bat`**（Edge 会再开一个页面），
第二个页面启动时会看到存储里那段"进行中"的现场，于是把它结算保存；
而第一个页面内存里还在继续计时，稍后停止时又会写一条——同一段时间被计了两次。

修法：**每段计时带一个唯一编号（`segmentId`）**，记录 id 由它推导（`rec-<segmentId>`），
写入时若同 id 已存在就跳过；存储层读取时也会对重复 id 去重。
这样即使两个页面都结算同一段，也只会留下一条记录。

### 新增/调整的自检用例（`tests/p4-timer.browser.test.js`，12 项 → 21 项；`p1-data.test.js` +1）

- 切走浏览器不会暂停，且在后台继续累计（直接调用 app 真实接线的那两个处理器：`__TT_HANDLE_HIDDEN__` / `__TT_HANDLE_CLOSE__`）
- 切到后台会刷新存储里的"最后落盘时刻"，心跳间隔在合理区间
- 关闭页面：够阈值保存、只算到关闭那刻、关闭后的等待不被补算
- 关闭页面：不足阈值直接丢弃，不留残留
- 真实刷新页面：那一段被结算成记录，不再有"暂停中"
- 暂停中关闭：已投入的部分照样保存
- 空闲时关闭：不产生记录、不留残留
- 异常退出：只按最后落盘时刻结算（20 秒而不是 30 秒），且会告知用户
- 异常退出且不足阈值：丢弃并提示
- **同一段被重复结算只记一条**（模拟"又开了一个页面"）
- 存储层：重复的记录 id 只保留第一条

**结果：全量 Node 86 + 浏览器 141 = 227 项全部通过。**

## P11 · 卡片「＋加时间」（第四轮）

**动机**：用户的原话是"我在这个项目上投入了几个小时，但我发现我没打开这个计时项目，
我就可以直接增加时长……不需要考虑专注度啥的，单纯的增加时长"。

改之前要补一段时长只能走：卡片 → `⋯` → 查看时间明细 → `＋ 手动补一条` → 填日期/时长 → 保存。
六步。**底层其实早就能用**——手动补录记录本来就计入累计/今天/本周与扇形图、不参与专注度、
也不受 2 分钟阈值限制。缺的只是入口太深。所以这一轮没有动任何数据口径，只做了"把入口提到卡片上"。

**改动范围**

| 文件 | 变化 |
| --- | --- |
| `js/ui/records.js` | 新增 `openQuickAdd(projectId)`；抽出共用的 `commitManualRecord` / `removeRecordById`；**修正**明细里手动补录行的专注度列 |
| `js/ui/home.js` | 新增 `quickAddButton()`，父卡片与子项目行的 `.pact` 里都插一个；`decorateButtons` 的动作白名单加 `quick-add` |
| `js/main.js` | `ACTION_BINDINGS` 的 `data-action` 映射加一条 `quick-add` |
| `css/app.css` | 卡片按钮与弹窗里快捷时长药丸的样式；窄屏收一收动作区间距 |
| `tests/manifest.json` | 新增 `P11` 阶段 |
| `tests/p11-quick-add.browser.test.js` | 新增 9 条用例（D8–D16） |

**为什么复用 `source:'manual'` 而不是新造一种记录类型**

手动补录这条路已经把需求里"不需要考虑专注度"表达清楚了：`js/calc.js` 只在 `source !== 'manual'`
的记录上累计专注度。复用它的直接好处是——累计/今天/本周、扇形图、明细合计、删除与导出的统计
全都不用改，存储格式与导入导出也一行没动。新入口和 `openRecordForm` 共用同一条写入路径
（`commitManualRecord`），两个入口的记录字段口径从此不会各写各的。

**几个取舍**

1. **药丸只填数字，不直接记账**。点一下 `+2 小时` 立刻落库当然更快，但加时长是"事后凭记忆补"的场景，
   记错日期的代价比多点一下大。所以右侧主按钮文案会跟着变成「加 2 小时」，让用户在下手前看到要加多少。
2. **不做"药丸选中高亮"**。输入框是唯一事实来源；药丸是只写不读的快捷键。否则手打数字之后
   高亮和数值就会对不上。
3. **三种卡片状态都显示这个按钮**（空闲/计时中/已暂停）。"忘了开计时"和计时器状态无关；
   按钮时隐时现还会造成布局跳动。计时中的卡片因此有 5 个动作元素
   `[秒表][暂停][停止][＋加时间][⋯]`，实测在窄屏也不换行。
4. **不在 `⋯` 菜单里重复放一条**。入口只放一处，避免"同一个动作两个位置"。

**顺手修掉的一个矛盾**

明细里手动补录行的「专注度」原本显示 `100%`——因为它没有暂停数据，`focusText(投入, 0)` 恒等于满值。
这和卡片上"手动补录不参与专注度"的口径直接打架：同一个项目，卡片不给专注度、明细却给 100%。
现在这一列对手动补录显示 `—`，和它左边的「暂停」列对齐。
`p7-records` 里那条用例的标题本来就写着「暂停/专注度为 —」，只是断言太宽（只查整行含 `—`）
没兜住这个矛盾，改完正好和它的原意一致。

**踩过的坑 / 值得记住的**

- `tests/p1-data.test.js` 会严格比对 `manifest.browserGlobals` 与 `tests/selftest.html` 的
  全局模块列表。**如果这次图省事新建一个 `js/ui/quickAdd.js`，就要同时改 4 处**
  （`manifest.json`、`tests/selftest.html`、`index.html`、`run-node-tests.mjs` 的 `GLOBAL_NAMES`），
  漏一处就红。放进已有的 `records.js` 一行登记都不用加。
- `beforeunload` 那类生命周期钩子这次没被碰到，但要注意：`openQuickAdd` 的确认分支会
  `close()` 之后再 `refreshDetail()`——后者在明细弹窗没开着时是空操作，所以从卡片进来的路径是安全的。
- 弹窗里那个只读的项目名用的是 `div` 而不是 `input`，所以 `modal.open` 的"聚焦第一个输入框"
  不会停在它上面。

**新增的 9 条用例**（`p11-quick-add.browser.test.js`）：入口存在且带对项目 id / 药丸只填数字不落库 /
确认后字段口径正确 / **加时间只增累计、专注度不动** / 日期可改过去且不计入"今天" /
0 时长与未来日期被挡住 / 撤销回退 / 子项目汇总到父项目 / 手动补录行专注度为 `—`。

**结果：新增 9 条浏览器用例全过；回归 Node 90 + 浏览器 143 全过。**

**给后续维护者的提醒**：给卡片加按钮前先确认没有测试在数卡片里的按钮个数。这次确认过——
`tests/` 里没有任何用例选中 `.pact`，所有选择器都是 `[data-project-card="x"] [data-action="start"]`
这种动作精确匹配，所以加一个带新 `data-action` 的按钮不会误伤既有断言。

## 第五轮修正：「⋯」是个死键，删除项目够不着

**用户报的现象**：项目卡片上的「⋯」点不动，找不到删除项目的入口。原话是"⋯里面没有删除"。

**不是删除功能坏了，是菜单点不开。** 两处缺陷叠在一起：

1. **卡片上的「⋯」按钮漏了 `data-action="menu"`**，只写了 `data-menu-for`。
   `main.js` 的事件委托只认 `[data-action]`，所以这个按钮从来没被接上过线——
   点它完全没有任何反应。
   `main.js` 里 `menu` 的处理函数一直写在那儿，但**全项目没有任何元素产生过
   `data-action="menu"`**：一段"注册了却永远不会被触发"的死代码。
   （我把所有 `data-action` 的产出点与消费点对了一遍，只有这一处对不上；
   其余按钮都正常。也就是说全项目只有这一个死键。）
2. **补上动作绑定后仍然点不开。** 菜单是挂在按钮**旁边**（兄弟节点，为了不被卡片宽度挤扁），
   而 `main.js` 的"点空白关菜单"用的是 `menu.contains(event.target)` —— 打开菜单的那一次
   点击冒泡到 document 时，target 是按钮、不在菜单里，于是被判定成"点了空白"，
   菜单刚建好就被关掉。实测确认：只打第 1 个补丁，菜单出现后 150ms 内就没了。

**为什么测试没抓到**：`p3-project-ui` 里那条用例是**直接调 `TTUI.projects.openMenu()`** 的，
绕开了真实点击。接口本身没问题，坏的是"按钮 → 接口"这根线，
而直接调接口的写法刚好把这段线跳过去了。

**改法**

| 文件 | 变化 |
| --- | --- |
| `js/ui/home.js` | 「⋯」按钮补上 `data-action: 'menu'`（并加注释说明两个属性各管什么） |
| `js/main.js` | "点空白关菜单"额外放过 `[data-menu-for]` 按钮自己 |
| `js/ui/projectActions.js` | 删掉 `openMenu` 自己注册的那个 document 监听器 |
| `tests/p3-project-ui.browser.test.js` | 原用例改成真实点击；新增 2 条用例 |

第 3 条单独说明：`openMenu` 原来会在 `setTimeout(0)` 里挂一个 `once` 的 document 监听，
意思是"下一次点击就关"。它和 `main.js` 那个监听器职责重复，而且有个坏毛病——
点**另一个项目**的「⋯」时，那个旧监听器会把**新打开**的菜单一起关掉。
既然 `main.js` 已经统一管这件事，就把它删掉，同一件事只留一个主人。

**验证**

- 真实浏览器（CDP）走完整路径：点「⋯」→ 菜单出现（编辑 / 在这个项目下新建子项目 /
  查看时间明细 / 删除）→ 点「删除」→ 确认框写明"1 个子项目、2 条记录、共 30 分"→
  确认 → 项目、子项目、全部记录都删掉，`ui.expanded` 清干净，提示条文案正确；
  接着点另一个项目的「⋯」菜单照常出现；点空白处能关掉。五项全过。
- **新用例确认是真守卫**：把 `data-action` 那行临时撤掉重跑 P3，3 条用例变红
  （正好是漏掉绑定的那几条），改回来即全绿。否则它只是"跟着代码一起写对"的摆设。

**新增 2 条浏览器用例**：点「⋯」能打开菜单、菜单里有删除、且打开那一次点击不会顺手把菜单关掉、
点空白处能关掉（回归）／ 走真实点击路径完成一次删除（⋯ → 删除 → 确认，B7 的端到端）。

**结果：Node 100 项 + 浏览器 169 项，失败 0。**

## 第六轮：刷新页面不该把计时结束掉（按用户反馈）

**用户报的现象**：计时中按 F5 刷新，回来发现那一段计时已经结束了。原话是
"我想改成刷新后计时不结束"。

**确认过的口径**（问过再动手，两条都定了）：

1. 只让**刷新**继续计时，**关掉浏览器/关掉应用仍然结束这一段**（不改成"一律继续"）。
2. 刷新用掉的那零点几秒**算作投入**（和"切走浏览器照常在后台走"保持一致，不必特意扣掉）。

### 根因：结算的时机选错了

旧实现把"关闭"和"刷新"当成同一件事处理：`pagehide` 一到就跑 `finalizeOnClose()`
把这一段结算掉。可 **`pagehide` 是刷新和关闭共用的一个事件，在那个时机根本分不出是谁**——
用户按 F5 和用户关掉浏览器，触发的是同一段代码。

所以正确的做法不是"在卸载时更聪明地判断"，而是**把判断挪到有答案的地方**：

| 时机 | 能知道什么 | 该做什么 |
| --- | --- | --- |
| 页面卸载（`pagehide` / `beforeunload`） | 只知道"我要走了"，**分不清刷新还是关闭** | 只落一次盘、留一个"正常告别"的记号，**不结算** |
| 新页面启动（`reconcileOnLoad`） | 知道"我是刷新出来的吗"（Navigation Timing 的 `reload`） | 是刷新 → 把那段接回来继续走；否则 → 结算这一段 |

于是 `finalizeOnClose` 整个删掉了：卸载时既然分不清，就不该由它做结算。
结算只剩 `reconcileOnLoad` 一条路，同一件事不再有两个主人。

### 顺带修掉的一个一直存在的隐患：结算时长会翻倍

改这轮时发现：存储里的快照本来记的就是**"截至最后一次落盘的总量"**
（`runtimeSnapshot` 写的是 `activeMsNow()`），可是读取它的 `reconcileOnLoad`
却按"base + 锚点时刻到现在"又加了一遍，于是**同一段时间被算了两次**。

这个 bug 从第二轮就在，只是**一直没人测到**：那几条用例是**手工构造**一份快照喂进去的，
口径写成了"base = 0 + 锚点"，恰好和真实存进存储的形状不一致——用例和实现各信各的，
于是两边一起错着还能全绿。这轮把口径统一成"存总量、读总量"，并让用例改用
**应用真的会写出来的那种快照**。

代价是：这轮改动之后，"关闭浏览器"这条最常走的路就会经过这段代码
（旧实现是 `pagehide` 直接结算，不经过它），所以这个隐患必须在同一轮修掉，
不能留着——否则用户只是关个浏览器，记录出来的时长就会翻倍。

### 另外一个必须挡住的坑：浏览器"恢复上次标签"也算刷新

浏览器"继续上次的标签页"是**重新加载**这些页面，Navigation Timing 报的同样是 `reload`。
要是照单全收，那么**关掉浏览器几小时后再打开，这几个小时会被当成投入记进去**。
所以加了一条时间窗（`RESTORE_WINDOW_MS = 60_000`）：现场躺了超过一分钟就不算刷新，
按老规则结算掉。刷新本身是一瞬间的事（本机页面不到 1 秒），一分钟绰绰有余。

### 改法

| 文件 | 变化 |
| --- | --- |
| `js/timer.js` | 删 `finalizeOnClose`、`activeMsAt`/`pausedMsAt`；新增 `isReloadNavigation`、`restore`；`heartbeat({closing:true})` 落盘时写 `closedAt`；`reconcileOnLoad` 分"刷新接回来 / 其它情况结算"两条路；统一快照口径（存总量、读总量） |
| `js/main.js` | `handleClose` 不再结算，改为"落盘 + 留告别记号" |
| `js/storage.js` | 运行时快照结构补上 `closedAt`（页面正常告别的记号），并做类型规范 |
| `tests/p4-timer.browser.test.js` | 新增 5 条（含真刷新）；改写 5 条旧的"关闭即结算"用例 |
| `说明.txt` | 给普通用户补上"刷新页面不算中断"这条规则 |

"正常告别记号"（`closedAt`）的用途：卸载时写下的时间戳。**被强杀时最后一次落盘一定没有它**，
于是下次打开能分清"用户自己关掉/刷新"和"进程被杀"——前者不该吓唬用户，
后者才需要提示"请确认这段时间是否准确"。

### 新增/改写的关键用例（P4：21 项 → 24 项）

- **真刷新（`location.reload()`）** → 计时继续、项目不变、不产生记录、卡片仍是"计时中"、
  刷新前后的投入算同一段（结束时只落一条记录）。
  注意测试里必须用 `location.reload()`：测试页原来的 `reloadApp()` 是**换网址重新加载**，
  浏览器算"导航"而不是"刷新"，用它永远测不到这条规则。
- **刷新时处于"暂停中"** → 刷新后仍是暂停中，这一段不结束。
- **卸载时（刷新和关闭都会触发）只留现场、不结算**：存储里仍是 `running`、
  带上 `closedAt`、没有记录，内存里也还在计时。
- **重新打开才结算，且只算到离开那一刻**：离开后故意等 2.5 秒再打开，
  记录里不能多出这 2.5 秒（C9）。
- **刷新接回来：投入量从离开那一刻接着走，绝不翻倍**：20 秒 + 离开的 3 秒 ≈ 23 秒，
  要是又犯"锚点加两遍"的毛病，这里会直接变成 40 秒以上。
- **现场躺了太久不当作刷新**：两小时前的现场即使浏览器报 `reload` 也不接回来，只结算当时的 20 秒。
- **被强杀**（快照里没有告别记号）→ 仍按最后一次落盘结算，并提示核对。
- **同一段被重复结算只记一条**：补一条"结算出来的时长 = 快照里那个总量"的断言，
  这条断言正是上面那个翻倍 bug 的守卫。

### 验证（新用例确实是真守卫，不是摆设）

照例把修复撤掉重跑，确认它们真的会红：

| 临时改坏什么 | 结果 |
| --- | --- |
| 让 `isReloadNavigation()` 永远返回 false（等于回到"刷新也结算"） | **2 条红**：正是"刷新后接着走""刷新时仍是暂停中" |
| 把快照口径改回"base + 锚点"（复原翻倍 bug） | **2 条红**：被强杀那条从 20 秒变 **40 秒**、躺太久那条同样 20 → 40 |

改回来即全绿。

**结果：Node 100 项 + 浏览器 172 项，失败 0。**（浏览器 169 → 172，全部加在 P4）
